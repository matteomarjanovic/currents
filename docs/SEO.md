# Currents search visibility

## Homepage and user guide

Keep the homepage focused on discovering, saving, and organizing visual inspiration. The redesign identifies `https://currents.is/` as canonical, including when a campaign adds query parameters. The dev Nginx config sends `X-Robots-Tag: noindex, nofollow`. The production Caddy config defines a permanent `www` redirect. The live `www` record was pointing at Cloudflare during the audit. At rollout, verify that it reaches the redirect or configure the equivalent redirect at Cloudflare, preserving the path and query. Verify the apex canonical, staging header, and search snippet with Search Console after release. [Canonical URL guidance](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls) · [Indexing controls](https://developers.google.com/search/docs/crawling-indexing/block-indexing)

After release, check field Core Web Vitals and compare performance for branded and product-category searches in Search Console. The local mobile comparison improved with smaller HTML and fewer hero image downloads. If mobile loading still needs work, profile how much of the signed-in application the public landing page downloads. [Core Web Vitals](https://developers.google.com/search/docs/appearance/core-web-vitals)

When the user guide ships, link to its index from the homepage footer. Add contextual links from the feature demos when the matching guide pages exist and the links help readers learn the feature. Give each guide a stable, public URL and a descriptive title based on a task someone might search for, such as organizing visual references or searching for images by color. Use screenshots and real workflows. Link to the relevant guide from related blog posts and use Search Console query data to decide which guides to expand. A `WebSite` schema entry and an absolute preview image URL are follow-up improvements for site identity and link previews. [Google Search Essentials](https://developers.google.com/search/docs/essentials) · [Site names](https://developers.google.com/search/docs/appearance/site-names)

## Proposal for website images on Bunny

Start by reusing the existing `cdn.currents.is` pull zone. Leave its `/img/` traffic, origin, optimizer parameters, and cache rules in place. Publish public website imagery under a dedicated path such as `/site-media/` on `currents.is`. A Bunny Edge Rule limited to that prefix can use `https://currents.is` as the origin. Use it for landing and blog images first, then for other public page images as they are updated. This keeps both origins explicit while sharing the hostname and optimizer. The existing image configuration is recorded in [the infrastructure migration](SCALEWAY_MIGRATION.md). [Bunny Edge Rules](https://bunny.net/docs/cdn/edge-rules) · [Bunny Optimizer FAQ](https://bunny.net/faq/)

Version changed files and give the versioned images long-lived immutable cache headers. Keep the original site paths working as the cache origin. Serve responsive widths through Bunny where that saves bytes, and compare the resulting crops with the checked-in WebPs before choosing which to optimize. Cache keys must distinguish transformation parameters and negotiated formats. Test a cold and warm request for several marketing images and an existing `/img/` URL, including a missing file, a width variant, and format negotiation. Keep the website rule limited to public image paths so it never caches HTML, auth requests, or cookies. A separate pull zone is useful if website assets eventually need independent cache policy, purge scope, or billing.

## Proposal for sitemaps and Google Images

Start with a small XML sitemap for canonical production landing, product, and blog pages. Add it to `robots.txt`, submit it in Google Search Console and Bing Webmaster Tools, and use meaningful `lastmod` values when the content actually changes. Add the guide pages as they publish. The basic sitemap can go live independently of user content. [Google sitemap guidance](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap) · [Bing sitemap guidance](https://blogs.bing.com/webmaster/2025/7/Keeping-Content-Discoverable-with-Sitemaps-in-AI-Powered-Search/)

Pinterest's public `robots.txt` advertises separate Pin and board sitemaps, including quality and engagement tiers. The advertised XML endpoints checked for this audit returned 404, so the entries inside them remain unverified. For Currents, start with a small separate image sitemap of public save detail pages. Each entry can use the canonical `currents.is/profile/{handle}/save/{rkey}` URL as its page and a stable `cdn.currents.is/img/...` URL as the image. Verify the CDN hostname in Search Console and ensure both the page and image are crawlable. [Pinterest robots.txt](https://www.pinterest.com/robots.txt) · [Google image sitemaps](https://developers.google.com/search/docs/crawling-indexing/sitemaps/image-sitemaps) · [Image SEO](https://developers.google.com/search/docs/appearance/google-images)

The current save pages already server-render route-specific titles and social metadata. Before including them in a sitemap, test that anonymous visitors receive the intended image in a standard HTML `<img>`, along with useful alt text and context. Use the same anonymous visibility and moderation rules as the public detail view. Exclude saves that require a content warning to reveal, along with deleted, restricted, or duplicate entries. Pick one eligible representative per visual identity where practical, while preserving independently useful collections as their own pages. Remove entries when eligibility changes and keep the corresponding page status or indexing directive in sync. Track the pilot in Search Console's Image search report before expanding and sharding the sitemap. Resolve the scope of public search-engine discovery for user saves before enrolling them.
