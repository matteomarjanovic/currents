# Currents — Claude Code Instructions

## Project overview

Currents is an open-source Pinterest alternative on the AT Protocol. Users save images into Collections. Two services:

- **`appview/`** — Go HTTP server, AT Protocol OAuth (indigo SDK), PostgreSQL + pgvector
- **`inference/`** — Python FastAPI server, image/text embeddings via SigLIP2 (`google/siglip2-base-patch16-naflex`)

Deferred-but-planned features live in `BACKLOG.md` — check it before proposing new work, and delete entries when they ship.

## Coding philosophy

Code minimalism is a core pillar of this project. Write the least code that correctly solves the problem. No abstractions for their own sake, no extra configurability, no defensive handling of cases that can't happen. If something can be deleted without breaking behavior, delete it (always ask before doing it).

## Design docs — read before proposing changes

Several subsystems have a companion doc that records **why** the design is what it is, including alternatives that were evaluated and **deliberately rejected**. The bullets under "Key conventions" describe what the code does; these docs say what not to re-propose. Read the relevant one *before* suggesting a redesign, not after — a suggestion that reopens a settled trade-off is worse than no suggestion.

| Topic | Doc | Settled decisions it records |
|---|---|---|
| Color & hybrid text+color search | `COLOR_SEARCH.md` | Color is a **hard filter, semantics the sole ranking** — score blending and reciprocal-rank fusion were evaluated and rejected (Cosmos case study: fusing the two "blends relevance and hue too much"; a cosine distance and a ΔE aren't comparable scales, and a picked color is a *requirement*, not a nudge). Also: why the coverage floor is hybrid-only, and why `colorMaxDeltaE` stays at 25. |
| Feed junk filter | `FEED_JUNK.md` | Training data, enabling the head, backfill, global-feed-only scope. |
| Ranking, search & personalization | `ML.md` | How images are embedded, how each search mode retrieves, how the feed ranks, what the personalization slider changes. |
| Moderation | `MODERATION.md`, `MODERATION_DEPLOYMENT.md` | Labeler DID, signed-label format, deployment steps. |
| Supporter tier | `POLAR.md` | Polar setup, sandbox testing. |

## Key conventions

- The inference server targets Apple Silicon (`DEVICE = "mps"`). When editing, preserve MPS/CPU fallback compatibility — avoid CUDA-only APIs.
- Embeddings from `/embed/image` and `/embed/text` share the same vector space (multimodal retrieval).
- The Go appview uses PostgreSQL with the pgvector extension for storing and querying embeddings.
- The appview indexes AT Protocol records via a TAP WebSocket listener (`appview/tap.go`). TAP is configured in docker-compose to filter `is.currents.*` collections and signal on `is.currents.actor.profile`. The `collection`, `save`, and `user` tables are populated by this listener, not by the HTTP handlers.
- The `collection` and `save` tables have no FK constraints on `author_did` or `collection_uri` — events arrive for all network users and ordering isn't guaranteed.
- **Visual identity** deduplicates images across saves. Every save gets a `visual_identity_id` FK pointing to a `visual_identity` row. Resolution happens in `appview/tap.go` (`handleSaveUpsert`): resave-of-known-save → same CID already in DB → novel image (fetch blob + inference). The inference server returns both the SigLIP2 embedding and image metadata used to populate width, height, and dominant-color palette. `visual_identity` holds the canonical blob reference, embedding (HNSW-indexed), dominant-color palette, and save count. `save_count` is maintained by a DB trigger; canonical re-election happens in Go (`DeleteSave`). If the inference server is unreachable, `visual_identity_id` is left NULL and the event is acked — backfill manually later.
- **Actor profiles** are indexed into the `user` table from two sources: `is.currents.actor.profile` TAP events (all active Currents users) and the OAuth callback (`ensureUserProfile` in `appview/auth.go` for the logged-in user). Avatar URLs are stored as `{CDN_URL}/img/{did}/{cid}` — routed through the appview's image proxy. The `user` table upserts on conflict, so profiles stay current.
- **XRPC endpoints** live in `appview/xrpc.go`. The appview's service DID is `did:web:{SERVICE_HOSTNAME}` (served at `/.well-known/did.json`) and is independent from `OAUTH_HOSTNAME`. `getActorCollections`, `getProfile`, `getCollectionSaves`, `getSaves`, `searchSaves`, `getRelatedSaves`, and `getFeed` use optional auth — session cookie for the first-party web client, Bearer JWT for PDS-proxied calls (`atproto-proxy`), unauthenticated otherwise. The `CDN_URL` env var sets the base URL embedded in image URLs in XRPC responses. Image URLs are always built from the save's own `author_did` + `pds_blob_cid` — the visual identity is internal only and never surfaced in XRPC responses.
- **Save flow**: saves are AT Protocol records written to the user's PDS, then indexed asynchronously by the TAP listener. The frontend never writes to the appview DB directly. For new saves, both the web uploader and the browser-extension clipper POST the image to the appview's `POST /save` endpoint (`CreateSave`), which uploads the blob to the user's PDS and writes the record. For resaves (saving an image that already exists on another user's PDS), the frontend calls `POST /resave` on the appview, which fetches the blob from the original author's PDS, uploads it to the viewer's PDS, and creates the record — avoiding CORS issues with cross-origin blob fetches. In both cases the TAP listener picks up the new record and populates the `save` table. Viewer save state in XRPC responses (`viewer.saves`) is hydrated by matching `pds_blob_cid` (content-addressed, so the same image bytes produce the same CID regardless of which PDS hosts the blob).
- **Extension entry points**: the clipper opens in one of two modes (`clipper.mode` in `extension/src/lib/clipper-store.svelte.ts`). *Single* is right-click-an-image or the injected Pinterest button; *multi* is the whole-page picker, reached by right-clicking anywhere (`save-page-images` context menu) **or clicking the toolbar icon** — which is why the extension has no `default_popup`, since a popup would swallow `action.onClicked`. Discovery lives in `collect-images.ts` and **the filter is the feature**: min 200px per side, aspect ratio within 4:1, laid-out and visible, not broken, http(s)/data only (`blob:` URLs are page-origin-scoped and unfetchable from the worker), deduped by resolved URL, capped at 100. Loosening those thresholds fills the grid with icons and sprites and the panel stops being usable. Deliberately out: CSS `background-image` scanning, `og:image`, and cross-origin iframes (`all_frames` would mount the overlay in every frame). The batch run lives in `MultiPicker.svelte`, **not** in the service worker: the content script awaiting `sendMessage` keeps the worker alive for free, which removes any need for a persisted queue or restart-resume; the price is that the dialog can't be dismissed mid-run (`clipper.locked`). Three saves at a time, aborting the rest on the first `rateLimited` response, since each save bills an `uploadBlob` + `createRecord` against the user's hourly PDS write budget. Note, labels and attribution live in one `SaveDetails.svelte` shared by both modes; in multi they sit behind a collapsed "Details for every image" row (with a filled-field count so a collapsed section can't hide state) and are stamped onto every image in the run. Alt text is the one field that stays per-image: bulk saves take each `<img>`'s own `alt` attribute from the page, single mode asks the network for it (`LOOKUP_ALT`).
- **Swiping between images**: opening a grid tile is a shallow route (`pushState` in `image-card.svelte`, overlay rendered from `page.state.save` by both layouts), so the grid stays mounted and its neighbours are already in memory. `masonry-grid.svelte` hands the run of visible items to `frontend/src/lib/save-sequence.svelte.ts` on each tile click (the list arithmetic lives beside it in the plain `save-sequence.ts`, so it's unit-testable — `vitest.config.ts` deliberately runs without the Svelte runtime), and the detail view's mobile image stage carries the `swipe` action (`frontend/src/lib/swipe.ts`) to move through it. The run **starts** as a snapshot, not a live reference (tapping the detail's own related rail refills that rail, and a live list would swap the run out mid-swipe). A grid that also passes its `loadMore` opts into growing that snapshot: it syncs newly loaded items in for as long as it owns the run (ownership is per grid instance, so a stale grid can't sync into a run it no longer owns), and the detail asks for another page within `SEQUENCE_LOOKAHEAD` of the end. That ask is the **only** thing that can extend a run — the grid's own scroll sentinel sits under a full-screen overlay and never comes into view while the detail is open, so a live reference alone would not have helped. The four page-level grids pass `loadMore`; the related rail and organize's similar-panel deliberately don't, so those runs end where they started. Other decisions worth not re-litigating: swipes `replaceState` rather than `pushState`, so back always returns to the grid instead of replaying every image; and the gesture ignores touches starting within 28px of either screen edge, because iOS's edge-swipe-back (enabled in the native shell) and Android's back gesture own that gutter and would otherwise make "previous" unreachable. A save not in the sequence (deep link, no grid behind it) leaves the gesture inert. The stage is a three-pane track: the current image is in flow and gives the stage its height, the neighbours are absolutely positioned a step out on either side so they ride the drag without affecting it. They are **rendered**, not merely cache-warmed — being in the DOM is what loads them, and they carry `loading="eager"` because lazy loading would hold them back until they were already sliding into view. That costs two extra image loads, so the panes render only at mobile widths (`IsMobile`) — an eager `<img>` inside a `display:none` subtree still downloads. Since every swipe resets the related rail, its **first** page is deliberately small (`RELATED_FIRST_PAGE` 12, `RELATED_PAGE` 50 thereafter): a full opening page of below-the-fold images competes with the one being looked at and with the neighbours being loaded for the next swipe.
- **Unsorted saves**: a save's `collection` is optional. A save with no collection is stored with `collection_uri = ''` (empty-string sentinel, not NULL — there's no migration) and is "unsorted": it surfaces only on the author's profile via `is.currents.feed.getUnsortedSaves` (the profile **Unsorted** tab), never inside any collection (collection-scoped queries join on real URIs, so `''` is naturally excluded from save counts / canonical embeddings / the personalized feed). The "Profile" row in the collection selector saves here. An image can be in a collection *and* unsorted simultaneously (independent save records, same blob). Unsorted is populated only by **explicit** saves to the profile — unsaving (removing a save from a collection or from the profile) deletes that save record outright (`DELETE /save/{rkey}`); there is no move-to-unsorted fallback.
- **Collection hierarchy** is exactly one level deep: a collection record's optional `parent` strongRef makes it a **section** of a root collection (indexed as `collection.parent_uri`; `getActorCollections` rolls a section's saves into its parent's `saveCount`, so never sum the two). `PUT /collection/{id}` takes a tri-state `parent`: absent keeps the current one (what the edit dialog sends), `""` promotes a section back to the top level, a URI nests it. The single-level rule is enforced from both ends — the target must be a root, and a collection that already holds sections can't become one. In organize mode the four actions (Edit / Create section / Move into / Delete) live in one `collection-actions.svelte`, rendered as a right-click menu on the sidebar rows and as a "…" dropdown beside the header breadcrumb (the only entry point on touch, where the breadcrumb's ancestors collapse into a "…" menu to leave room). Deleting cascades to the sections and every save inside them, which is what the confirm copy has to say.
- **Starred collections** are stored in the `starred_collection` table (viewer_did + collection_uri PK). The `getActorCollections` and `getCollectionSaves` endpoints hydrate viewer state (`starred`) when the request is authenticated.
- **`searchSaves`** embeds the query text via the inference server (`/embed/text`) and runs pgvector ANN search (`<=>` cosine distance) over `visual_identity.embedding`. Offset-based pagination.
- **`getFeed`** returns a discovery feed. Global mode (unauthenticated or `personalized=0`): all images ranked by time-decayed popularity — `visual_identity.saver_count` (distinct saving users, maintained by the same DB trigger as `save_count`) × `exp(-0.1 × age_in_days)`, with a ±20% jitter seeded per (uri, day) so the top rotates daily while offset pagination stays stable within a day. Saves with NULL `created_at` are excluded. Personalized mode (`personalized=0–1`): the viewer's top collections are ranked by a time-decayed importance score (PinSage formula), each collection's precomputed `canonical_embedding` (medoid of its saves' embeddings) drives a pgvector ANN search, and results are blended with the global pool proportionally. The `canonical_embedding` on each collection row is updated in the background by a debounced goroutine in `tap.go` (30 s delay after save arrival).
- **Feature announcements** ("new feature" dots) are per-user and server-backed so they follow the user across browsers/devices. The `seen_feature` table (`viewer_did` + `feature_key` PK) records what each user has dismissed; `feature_key` is an arbitrary string owned by the frontend, so announcing a new feature needs **no backend change**. Endpoints: `GET /api/features/seen` → `{seen:[...]}` and `POST /api/features/seen/{key}` (both session-cookie auth, in `appview/features.go`). The web client mirrors this in `frontend/src/lib/stores/features.svelte.ts`: declare a `FEATURE_*` key constant, add it to `ACTIVE_ANNOUNCEMENTS` (an inventory, not a driver — nothing reads it at runtime), show an indicator where `!isFeatureSeen(key)`, and call `markFeatureSeen(key)` when the user engages (e.g. opens the feature's page). `loadSeenFeatures()` unions into the set (flags are append-only); indicators are gated on `features.loaded` to avoid flashing. **Brand-new accounts don't get every dot at once**: the announcements double as onboarding, so a first login (`ensureUserProfile` in `appview/auth.go` — detected by the absence of an `is.currents.actor.profile` record on the PDS, i.e. the moment the account becomes a Currents account) pre-dismisses everything listed in `onboardingSeenFeatures` (`appview/features.go`) via `SeedSeenFeatures`, keeping only the few worth pointing a newcomer at (currently Pinterest import + organize mode). Existing users are untouched.
- **Pinterest import is lossy at the source, by Pinterest's choice.** `BoardFeedResource` — the logged-out board grid the listing stage paginates (`appview/pinterest.go`) — silently omits pins the board genuinely holds; measured at **~9% of an account** (673 of 7,168 across 99 boards), ranging 0–37% per board. This has been investigated and is **not** ours to fix: it is not pagination, `page_size`, `field_set_key`, a missing `orig` image, a recency lag, dead images, or dedup, and it is **not** a content/moderation filter (the worst-hit boards are innocuous ones like "Presidents" and "Mothers", while swimwear boards are among the cleanest). The omitted pins carry no attribute distinguishing them from the ones that come through, and pins saved in the same *minute* differ. Ground truth came from the legacy widget API (`https://widgets.pinterest.com/v3/pidgets/boards/{user}/{board}/pins/`), which returns the board's true count and the missing pins — but it caps at ~50 with no pagination and no `orig` size, so it is a diagnostic, not a replacement. Because the loss is invisible, `import_job.expected_count` records Pinterest's own `pin_count` at queue time and `getImportSession` returns it as `expected`, so the progress UI can report the shortfall instead of showing a partial import as complete. It is recorded **only for whole-board jobs** — section jobs and section-filtered board jobs import a subset by design, so they store 0 ("unknown") and report nothing rather than inventing a phantom gap. Closing the gap for real needs an authenticated listing path (the pins are visible to a logged-in viewer), which is why the browser extension is the natural home for it.
- **Moderation** is built around an in-process atproto labeler (`appview/labeler_*.go`) that signs `com.atproto.label.defs#label` records and serves them via standard `subscribeLabels` / `queryLabels` endpoints. Three-axis auto-classification (NSFW / violence / AI-generated) happens inside the existing `/embed/image` SigLIP2 pass — no extra GPU work. Scores cross thresholds in `appview/moderation.go` (`ClassifyHarmScore`, `IsAIGenerated`) to drive a `currents-{nsfw,violence}-suspected` or `currents-ai-generated` label plus an entry in `review_item`. State is keyed by **exact blob CID** (`blob_moderation_state.blob_cid` = `save.pds_blob_cid`), NOT by visual identity — exact-bytes dedup is what we want for moderation. Read queries (search, related, feed, by-uri, collection saves) all exclude `harm_state='blocked'` blobs; the `<LabeledMedia>` Svelte wrapper blurs/badges/hides based on the labels XRPC hands back, resolved against the viewer's **per-user moderation preferences**. Those preferences are server-backed (so they follow the user across browsers/devices/mobile): the `moderation_pref` table holds one row per user (defaults: adult axes `blur`, AI-generated `show`), exposed via `GET`/`PUT /api/moderation/prefs` (session-cookie auth, in `appview/moderation_prefs.go`) and mirrored client-side in `frontend/src/lib/stores/moderation-prefs.svelte.ts` (loaded once on mount, optimistic `PUT` on each change). Absence of a row means the user is on the defaults — no migration-time provisioning of existing users. Admin endpoints under `/api/admin/*` (gated by the `moderator` table) drive the human review workflow at `/admin/queue`. The labeler's DID, service endpoint, and signed-label format are documented in `MODERATION.md`; deployment steps (DNS, keypair, service-record publishing) live in `MODERATION_DEPLOYMENT.md`.
- **Search by color**: the inference server extracts each image's 5-color palette in CIELab (over-cluster k-means → merge within ΔE 10 → select by coverage × chroma, so small saturated accents survive; `_dominant_colors` in `inference/main.py`, also exposed standalone at `POST /palette`). The appview indexes the canonical palette per visual identity in `visual_identity_color` (one row per color: `lab VECTOR(3)` + coverage `fraction`, HNSW `vector_l2_ops` — L2 in Lab ≈ ΔE76), populated in `processBlobEnrichment` (`SetVIColors`). `searchSavesByColor` (supporter-gated, mandatory auth) converts the query hex to Lab in Go (`hexToLab` in `appview/visual.go` — the single definition of the color space, used for both indexing and queries; the inference contract stays hex-only) and ranks by `ΔE − colorCoverageWeight × fraction` over an ANN candidate scan deduped per visual identity (tunable constants in `pgstore.go`). Optional `library`/`collections` params scope the search to the viewer's saves. Pre-existing images need `appview backfill-colors` to appear in results. An optional `q` turns this into **hybrid text+color search** (`SearchHybridSavesPage`): the color is a hard filter — palette color within `colorHybridMaxDeltaE` (20) **and** covering at least `colorHybridMinFraction` (0.05) of the image — and semantic distance is the sole ranking. Both thresholds are hybrid-only and stricter than pure color search's `colorMaxDeltaE` (25): pure color search demotes weak matches through its `− colorCoverageWeight × fraction` ranking, while hybrid orders by semantics alone so its gate is the entire color criterion, and it can afford strictness because the text query carries recall — but only so far, since too tight a gate starves the semantic ranker of on-topic candidates (the coverage floor is the hue-neutral recall dial; ΔE is the one that trades against muted queries). **Read `COLOR_SEARCH.md` before proposing any change to color ranking or filtering** — score blending and rank fusion are already-rejected designs, and it records how each threshold was chosen plus the one known limitation a threshold can't fix (neutrals contaminating low-chroma queries, since ΔE76 puts grey ≈ the query's own chroma away).
- **Feed junk filter**: the global discovery feed excludes content-type junk (QR codes, UI screenshots, scanned documents). A binary classification head (`feed_junk_head.onnx`, trained in `moderation/04_feed_junk_head.ipynb` on public datasets: Rico screenshots + RVL-CDIP documents + synthetic QR codes vs COCO/WikiArt) runs inside the existing `/embed/image` SigLIP2 pass — no extra GPU work — and standalone at `POST /classify/junk/embeddings` for backfill. The junk probability is stored on `visual_identity.junk_score` (NULL = unscored, always passes); `GetGlobalFeedSaves` excludes rows at or above `feedJunkScoreMax` (tunable in `pgstore.go`, no re-scoring needed) — global feed only, library/search/profiles never hide anything. The head is optional: a missing ONNX in `MODELS_DIR` (or `FEED_JUNK_HEAD_ONNX`) leaves scoring off and the gate dormant. Pre-existing images need `appview backfill-feed-junk`.
- **Supporter tier (Polar)**: semantic library search (`searchLibrarySaves`), find-similar-in-library (`findSimilarInLibrary`), and search-by-color (`searchSavesByColor`) are gated behind a Polar subscription ($7/month, $70/year — two products, one price each). The gate is switched on by setting `POLAR_WEBHOOK_SECRET` on the appview — unset means every authenticated user passes, so dev needs no Polar account. `POST /api/polar/webhook` (`appview/supporter.go`) verifies the Standard-Webhooks signature and upserts every `subscription.*` event into `polar_subscription`, mapping the subscription to a user via the customer's `external_id` (the viewer's DID, stamped by the appview when it creates the checkout session at `POST /api/supporter/checkout`); entitlement = any row with status `active`/`trialing`/`past_due`. Gated XRPC handlers call `requireSupporter` and answer `403 SupporterRequired` (declared in the lexicons). Color search is the exception: it goes through `requireColorSearch`, which lets non-supporters sample it on a lifetime allowance of `colorTrialLimit` (5) **distinct query colors** before falling back to the same 403. The ledger is the `color_trial` table (viewer_did + color_hex PK), charged in `appview/supporter.go` only after the hex parses; a color within `colorTrialSameDE` (ΔE76 5) of one already spent is free, so paginating a result set, adding a text query, narrowing the scope or nudging the picker by a shade never costs a second trial. The web client mirrors `GET /api/supporter/status` → `{active, subscribed, colorTrialsLeft}` into `frontend/src/lib/stores/supporter.svelte.ts` (`active` drives the gate and is true for everyone while the gate is off; `subscribed` is the real Polar state driving the settings UI; `colorTrialsLeft` is refreshed at each gate check and rendered by `color-trial-note.svelte` under both color panels) and opens `supporter-dialog.svelte` (Polar embedded checkout via `$lib/polar.ts` + `@polar-sh/checkout`, plans in the shared `supporter-plans.svelte`) when a non-supporter clicks "Find similar in library" or starts typing in the library search command. Server-side Polar calls (checkout + customer-portal sessions) go through the `polar-go` SDK, configured with `POLAR_ACCESS_TOKEN` and `POLAR_SERVER` (`sandbox`/`production`). Subscription management happens in Polar's customer portal: `POST /api/supporter/portal` mints a customer session and returns its URL. The public manifesto/pricing page at `/support-currents-project` shows live transparency numbers from `GET /api/supporter/stats` (public: total users + supporter counts per product id; the client maps product ids to dollars). Subscriber status is also surfaced as a `supporter` boolean on user-facing views (`getProfile`, `searchActors`, and `getImageCollections` authors — batch-hydrated via `SupporterDIDs`, real subscriptions regardless of the gate switch) and rendered with `supporter-badge.svelte` (a "negative" pink heart — the Currents wave carved inside a pink heart outline; self-colored via `fill-pink-500`/`stroke-pink-500`, so it ignores the surrounding text color — size it with `size-*`, don't pass `text-*`). Setup and sandbox-testing steps live in `POLAR.md`.
- **Settings live in a dialog, not a page**: `frontend/src/lib/components/settings-dialog.svelte` (sidebar-in-dialog layout; sections: Moderation, Subscription, Account), mounted once in the root `+layout.svelte` and opened from anywhere via `openSettings(section?)` in `frontend/src/lib/stores/settings.svelte.ts` (explore top bar, organize sidebar, and blurred-media "change settings" links all use it). Add a new settings area by extending the `NAV` list and the section markup there.
- **Account deletion**: `POST /api/account/delete` (session auth, body `{"deletePdsData":bool}`, in `appview/account.go`) answers 409 while a real Polar subscription is active (the settings Account section blocks the button and links the billing portal), removes the repo from TAP tracking via TAP's admin API (`POST {TAP_ADMIN_URL}/repos/remove`, Basic auth `admin`/`TAP_ADMIN_PASSWORD` — when that password is set TAP also gates its WebSocket, so the listener dials `/channel` with the same credentials), then wipes every DB row keyed to the DID (`DeleteUserData` in `pgstore.go`; saves loop through `DeleteSave` to reuse canonical re-election). Kept on purpose: follows *of* the user, other viewers' favourites of their collections (both are the other users' records, hidden by joins until the user returns), and all moderation/audit tables. PDS records stay by default: on a later login the OAuth callback sees the user row missing and calls `/repos/add`, and TAP backfills the repo (the signal collection alone wouldn't re-add it — it only fires on new events). With `deletePdsData` a `pds_wipe` job row is queued and `PdsWipeWorker` deletes every `is.currents.*` record from the user's PDS in the background — `applyWrites` batches of 200 deletes, backing off on 429 (PDS write budget: 5,000 points/hour, 35,000/day, DELETE = 1 point) — keeping one oauth session alive until done and aborting if the user logs back in mid-wipe.

## Running locally

```bash
# Full stack (appview + db)
SESSION_SECRET=<secret> docker compose up --build

# Inference server only
cd inference && uvicorn main:app --reload
```

## Common tasks

- **Add a new inference endpoint**: edit `inference/main.py`, follow the existing pattern (queue-based batching for text, direct executor for images).
- **Add a DB migration**: add a new numbered file to `appview/migrations/` (e.g. `006_*.sql` + `006_*.down.sql`). golang-migrate applies them in order on startup.
- **Handle a new TAP collection**: add a case to the `switch ev.Collection` in `handleTapRecord` in `appview/tap.go`, define a record struct, and add store methods in `appview/pgstore.go`.
- **Add a new XRPC endpoint**: define the lexicon in `lexicons/is/currents/`, add the handler to `appview/xrpc.go`, and register the route in `appview/main.go`. Use `srv.AuthValidator.Middleware(handler, true)` for mandatory auth, or `s.optionalAuth(r)` inside the handler for optional auth.
- **Change the embedding model**: update `CHECKPOINT` in `inference/main.py`, verify the processor API is compatible, and update the `VECTOR(768)` dimension in the migration if the output size changes.
- **Backfill missing visual identities**: query `SELECT uri FROM save WHERE visual_identity_id IS NULL` and re-process those saves through the inference pipeline.
- **Backfill moderation**: `appview backfill-moderation [--dry-run] [--limit N]` re-scores existing saves through `/classify/safety/embeddings`. Idempotent; honors Ctrl+C.
- **Backfill feed junk scores**: `appview backfill-feed-junk [--dry-run] [--limit N]` scores existing visual identities' stored embeddings through `/classify/junk/embeddings` — no blob fetches or backbone passes. Idempotent; honors Ctrl+C.
- **Backfill colors**: `appview backfill-colors [--dry-run] [--limit N] [--concurrency N] [--rate N]` re-extracts palettes through `/palette` and populates `visual_identity_color` (plus refreshes `save.dominant_colors`). Runs a worker pool (default 8) under a global token bucket (default 20 img/s) — each item is a PDS round trip plus a ~100 ms palette call, so it's latency bound and the sequential version managed ~1 img/s. Idempotent; honors Ctrl+C; failed items stay in the pool, so rerun until the pending count stops dropping.
- **Run tests**: `cd appview && go test ./...` (pure-function tests, no DB needed). Set `TEST_DATABASE_URL=postgres://appview:appview@localhost:5432/appview_test` to also run the DB-backed store regression tests against the dev compose Postgres — the suite creates that database itself, wipes its schema, and runs every migration from scratch (the name must end in `_test`). `cd inference && ./venv/bin/python -m unittest -v` (palette extraction + image decode/prepare regression tests, no model load). Clustering: `docker compose -f docker-compose.dev.yml run --rm --build clustering python -m unittest -v` (the deps only exist in the service image). Frontend: `cd frontend && npm run test:unit` (vitest, pure TS modules) and `npm run test:e2e` (Playwright, mocked API).
- **Write regression tests with behavior changes**: store queries and query rewrites get a test in `appview/pgstore_db_test.go` (DB-backed, pins result semantics — rollup counts, ordering, viewer hydration, exclusions); pure Go helpers get table-driven tests next to their file; Python helpers get unittest cases in a `test_*.py` beside the module (inference: run in the venv; clustering: run in the service image); frontend pure logic gets a vitest `*.test.ts` beside the module; user-visible flows get a Playwright spec in `frontend/e2e/`.
- **Tune moderation thresholds**: edit constants in `appview/moderation.go` (`ThresholdAutoSuspected`, `ThresholdReview`, `ThresholdAIGen`). Both live TAP and backfill share the ladder via `ClassifyHarmScore` / `IsAIGenerated`.
- **Add a custom label value**: declare it in `app.bsky.labeler.service` (see `MODERATION_DEPLOYMENT.md`), add constants in `appview/moderation.go`, and update the blur/badge sets in `frontend/src/lib/components/labeled-media.svelte`.
- **Announce a new feature** (one-time "new" dot): add a `FEATURE_*` key constant to `frontend/src/lib/stores/features.svelte.ts` and list it in `ACTIVE_ANNOUNCEMENTS`, render an indicator gated on `!isFeatureSeen(key)` where the feature is surfaced, and call `markFeatureSeen(key)` when the user engages with it. No DB/endpoint change needed — keys are free-form (the `seen_feature` table stores whatever the frontend posts). Decide whether new sign-ups should see it too: if not (the usual answer for anything that isn't a first-session action), add the key to `onboardingSeenFeatures` in `appview/features.go`. Remove the key from `ACTIVE_ANNOUNCEMENTS` once it's no longer newsworthy.
- **Gate a feature behind the supporter tier**: server side, call `s.requireSupporter(w, r, did)` after the auth check in the handler and declare the `SupporterRequired` error in the endpoint's lexicon. Client side, run the action through `requireSupporter()` (see organize `+page.svelte`) — it checks the `supporter` store and opens `supporter-dialog.svelte` for non-supporters. No new Polar config needed; the tier is one subscription. Color search instead pairs `requireColorSearch` (server) with `requireColorSearch()` (client) so the paywall only appears once the free trial colors are spent.
